講師からのお題：本物のログインにしよう

Webツール開発ワークショップの追加のお題です。講師がお題を出したら取り組みます。

0. 講師からのお題

今のツールのログインを、Clerk（クラーク）という外部のサービスを使った本物のログインに置き換えてください。

なぜやるのか

今のツールのログインは、メールアドレスを入力するだけの簡易版です。API は、送られてきたメールアドレスをそのまま本人とみなしています。そのため、他人のメールアドレスを入れれば、その人になりすませます。[7] の相互レビューで「なりすませた」と指摘された班もあるかもしれません。

実際のサービスでは、ログインの仕組みを自分で一から作ることはあまりありません。パスワードの保存や、ログイン状態の管理を間違えると、そのまま情報漏えいにつながるからです。そこで、ログインを専門に引き受ける外部のサービスと連携するのが一般的です。このお題では、その連携を体験します。

✅ ゴール

  1. Clerk のサインイン画面からログインできる。ログインしないとツールを使えない
  2. API は、Clerk が発行した「ログイン済みの証明書」を確かめて本人を決める。他人になりすませない
  3. 公開した URL でも、同じようにログインして使える

進め方と目安

手順やること目安
1Clerk の仕組みを知る（この資料を読む）10分
2鍵とログインの方法を確かめる5分
3Claude Code で導入する30〜40分
4手元と公開先で確かめる15分

本編と同じく、いきなり実装を頼まずに spec.md を直してから実装します。何をどう変えるかを決めるのは自分たちです。

1. Clerk とは

Clerk は、ログインの仕組みをまるごと引き受けてくれるサービスです。サインイン画面、ユーザーの登録と管理、ログイン状態の管理を Clerk が用意してくれます。自分たちが書くのは、「このリクエストは本当にログインした本人から来たか」を確かめる部分だけです。

Clerk のサーバーは、世界中のたくさんのサービスのログインを同時に引き受けています。そのため Clerk を使うには、「このツールのログインを引き受けてほしい」という登録が必要です。Clerk ではこの登録を「アプリケーション」と呼びます（プログラムを作るという意味ではありません）。登録ごとに、次のものが分かれます。

  • ユーザーの名簿（ほかの登録のユーザーとは混ざらない）
  • ログインの方法（Google アカウント、メールに届くコード など）
  • ログインを受け付けるサイト（URL）
  • 鍵（下の「3種類の鍵」）

ログインの流れ

① Clerk の画面でログイン→② Clerk が証明書を発行→③ 画面が API に証明書を送る→④ API が証明書を確かめる
  1. ログイン：利用者は、Clerk が用意したサインイン画面でログインします。
  2. 証明書の発行：ログインに成功すると、Clerk が「この人はログイン済みです」という証明書（セッショントークン。JWT という形式）を発行します。証明書には Clerk の署名が付いていて、書き換えると署名が合わなくなります。
  3. API を呼ぶ：画面は、API を呼ぶたびに証明書を一緒に送ります。
  4. 確かめる：API は、証明書の署名が本物か、有効期限が切れていないかを確かめます。本物なら、証明書に書かれたユーザー ID を本人とみなします。

今の簡易ログインとの違い

今の簡易ログインClerk
本人をどう決めるか送られてきたメールアドレスを、そのまま信じる（自己申告）Clerk の署名付きの証明書を確かめる
なりすまし他人のメールアドレスを送ればできる証明書を偽造できないので、できない
サインイン画面自分たちで作った入力欄Clerk が用意した画面

3種類の鍵

Clerk には鍵が3種類あります。今回使うのは、公開してよい2つだけです。

鍵使う場所役割公開してよいか
Publishable key画面どの登録（アプリケーション）のログインかを、Clerk に伝えるよい
JWKS Public Key（公開鍵）API証明書の署名が本物かを確かめるよい
Secret key（今回は使わない）Clerk の管理機能を操作するだめ

公開鍵は「鍵を開ける」ためではなく、「署名が本物か確かめる」ための鍵です。署名を作れるのは Clerk だけで、公開鍵を知っていても証明書は偽造できません。だから公開してよいのです。今回は秘密の値を使わないので、Cloudflare に何かを登録する必要もありません。

2. 準備

ログインの処理は Clerk のサーバーが行います。Clerk への登録（アプリケーション）は講師が済ませてあります。登録すると発行される鍵のうち、使う2つは、講師がリポジトリ直下の clerk-keys.md に入れてあります。自分で貼り付ける必要はありません。

  • Publishable key（pk_test_ で始まる1行）
  • JWKS Public Key（-----BEGIN PUBLIC KEY----- で始まる複数行）

中身は、Claude Code に「clerk-keys.md を見せて」と頼むと確かめられます。

どちらも公開してよい値なので、コードの中に書いて commit して構いません。本編の「秘密の値を渡さない」には当たりません。

ログインの方法

ログインには、ユーザー名とパスワードを使います。メールアドレスは要りません。初めてのときは、サインイン画面の「Sign up」から登録します。

  • ユーザー名：英数字で4文字以上（数字だけは使えない）
  • パスワード：8文字以上。よく使われるパスワード（password123 など）は使えない

「別のアカウントでログインし直す」確認（4. 確かめる）のために、ユーザーを2つ作っておくと便利です。

3. 導入する

3つのプロンプトを順に Claude Code に送ります。1つ終わるごとに、内容を確かめてから次へ進みます。

① spec.md を直す

Claude Code に送る
ログインを、メールアドレスを入力するだけの簡易ログインから、Clerk を使った本物のログインに変えたい。
まず spec.md の「機能」「ルール」「画面」をどう直すかの案を見せて。
- ログインは Clerk のサインイン画面で行う。ログインしていない人はツールを使えない
- 本人は、Clerk のユーザー ID で決める（メールアドレスでは決めない）
- 今あるデータはダミーなので、消してよい
私たちが OK と言ったら spec.md を直して。実装はまだしないで。

② 画面に Clerk を入れる

Claude Code に送る
spec.md に合わせて、frontend/ に Clerk を入れて。
- React 用の Clerk の部品（@clerk/clerk-react）を使う
- Publishable key は、リポジトリ直下の clerk-keys.md に書いてある値を使う。公開してよい値なので、frontend/src/ の設定用のファイルに定数として書く
- 今のメールアドレスを入力するログインを、Clerk のサインインに置き換える
- ログインしていないときは、Clerk のサインイン画面を出す
- 画面の右上などに、ログイン中のユーザーとサインアウトのボタンを出す
- API を呼ぶときは、Clerk のセッショントークンを Authorization ヘッダ（Bearer）に付ける。x-user-email は送らない

③ API で証明書を確かめる

Claude Code に送る
backend/ の API で、x-user-email を本人とみなすのをやめて、Clerk のセッショントークンを確かめて本人を決めるようにして。
- Authorization ヘッダのトークンを、リポジトリ直下の clerk-keys.md に書いてある公開鍵（JWKS Public Key）で検証する。Secret key は使わない
- 公開鍵は公開してよい値なので、backend/src/ の設定用のファイルに定数として書く
- 署名、有効期限（exp と nbf）、どのサイトから来たか（azp）を確かめる。azp で許可するのは、次の2つ
  http://localhost:8787
  <自分たちの班の公開 URL（例：https://team-a.xxxx.workers.dev のように https:// から書き、最後に / を付けない）>
- 確かめられないときは 401 を返す
- 本人の識別には、トークンの sub（Clerk のユーザー ID）を使う。テーブルの変更が要るなら backend/migrations/ に足す
- wrangler.jsonc、scripts/、package.json の scripts は変更しない
- 確かめるために手元のサーバーを起動したら、終わったあとに必ず止める（私たちが別のターミナルで起動するため）

実装が終わったら、次の2つを報告して。
1. トークンを付けずに API を呼ぶと 401 になること
2. x-user-email に他人のメールアドレスを入れて API を呼んでも、なりすませないこと

プロンプトに出てくる言葉：Authorization ヘッダ（Bearer）は、証明書を API に渡すときの決まった書き方です。azp は、証明書に書かれた「どのサイトの画面でログインしたか」で、許可していないサイトから来た証明書を断るために確かめます。sub は、証明書に書かれたユーザー ID です。

終わったら、本編の [4] と同じく、2つ目のターミナル（コンテナの中）のリポジトリ直下で1行ずつ実行して、手元で確かめます。テーブルを変えたときは、npm run db:migrate:local も忘れずに実行します。

ターミナルで実行
npm install
npm run db:migrate:local
npm run build
npm run dev

4. 確かめる

手元で（http://localhost:8787）

  • ログインしていないと、Clerk のサインイン画面が出て、ツールが使えない
  • ログインすると、今までどおり ①〜④ が一通りできる
  • 別のアカウントでログインし直すと、「自分のデータ」が切り替わる
  • DevTools の Network タブで、/api/... のリクエストに Authorization ヘッダが付いている

公開先で

  • main に push して数分待ち、公開した URL でも同じようにログインして使える

テストのスキルで（本編の [8] で作った班）

Clerk を入れると、API はログインの証明書が無いリクエストをすべて断るようになります。そのため、前のテストの項目はそのままでは ✕（401）になります。次のプロンプトで、テストの項目を Clerk に合わせて直してから流します。

ここで確かめるのは、「ログインしていないと断られる」「なりすませない」の2つです。題材のルールが守られているかは、Clerk を入れる前の本編 [8] で確かめ済みなので、ここでは流しません。

Claude Code に送る
Clerk を入れたので、tests.md のテストの項目を直して。
- ログインの証明書（Authorization ヘッダ）が無いリクエストは、401 になることを確かめる項目を足す
- x-user-email に他人のメールアドレスを入れて送っても、なりすませないことを確かめる項目を足す
- ログインの証明書が要るほかの項目は、今回は「手元では確かめない」と書いて残す
直したら、テストのスキルを流して、結果を見せて。

確かめられたら commit して、main に push します。

5. 困ったとき

  • 画面に「Development mode」などの表示が出る → 開発用の設定で動いているための表示です。問題ありません。
  • 手元ではログインできるのに、公開した URL ではログインできない → 公開した URL を Clerk 側で許可する設定が要ります。講師に伝えてください。
  • ログインしているのに API が 401 を返す → 画面が API にトークンを付けていないか、azp で許可するサイトが合っていない可能性があります。エラーと「何をしたら何が起きたか」を Claude Code に貼って相談してください。
  • 鍵が違うと言われる → clerk-keys.md の Publishable key は画面、公開鍵は API で使います。逆になっていないか、Claude Code に確かめてもらってください。

✅ 完了の定義

  1. ログインしないとツールが使えず、Clerk のサインイン画面が出る
  2. トークンを付けずに API を呼ぶと 401 になり、他人のメールアドレスを送ってもなりすませない
  3. 公開した URL でも、ログインしてツールが使える
