Webツール開発ワークショップ

Claude Design と Claude Code を使って、社内向けの小さな Web ツールを画面 → フロント → バックエンドまで一通り作ります。

0. この資料について

  • 説明：約1時間（この資料をざっと読む）
  • 作業：約3〜4時間（班で1つのツールを作る）
  • 前提：Claude Code の基本操作は Day1 で説明済み。必要な準備は下の「事前準備」を見てください。

この資料は作業中に横に置いて使うものです。手順ごとにコピーして使えるプロンプトを置いてあります。< > の部分を自分の題材に書き換えて使ってください。

黒い枠の上のラベルで、どこで使うものかを区別しています。

  • Claude Design に送るClaude Code に送る：チャット欄に貼り付けて送るプロンプト
  • ターミナルで実行：ターミナルに1行ずつ打つコマンド。Claude には送らない
  • 参考（実行しない）：説明のための図や例

✅ ゴール（ここまでできたら完成）

  1. メールアドレスでログインできる
  2. データを登録できる
  3. 登録したデータが一覧に出る。ページを再読み込みしても消えない（DB に保存されている）
  4. 題材ごとの固有ロジックが動き、ルール違反の操作はAPI 側でも弾かれる
  5. 公開したツールを別の班に使ってもらい、もらった意見をもとに直す

事前準備

  • アカウント：Claude（Pro 以上）、GitHub（講師の Organization への招待を受けておく）。Cloudflare（無料）は班の代表者1人だけ必要です（[6] で使います）
  • ツール：Claude Code、Node.js 24 以上、git。Cloudflare の CLI（wrangler）はリポジトリの backend/ に入っているので、別にインストールしなくてよい

リポジトリには、講師が次のファイルを入れてあります。自分で作る必要はありません。中身と意味だけ確認してください。

参考（実行しない）
リポジトリ直下/
├── .github/workflows/deploy.yml  ← 自動で公開する仕組み（[6]）
├── .claude/settings.json         ← ① Claude Code にさせない操作の設定
├── .npmrc                        ← ② 怪しいパッケージを入れない設定
├── .gitignore                    ← commit しないファイルの一覧
├── CLAUDE.md                     ← Claude Code への注意書き（触らないファイルとその理由）
└── backend/                      ← バックエンドの雛形（[4] でここに API を書く）
    ├── wrangler.jsonc            ← 公開先と DB の設定
    ├── package.json
    ├── src/index.ts
    └── migrations/               ← 空。[4] でテーブル定義を足す

.github/、.claude/、backend/wrangler.jsonc、backend/package.json の scripts は講師が管理しています。変更しないでください。変更すると公開が壊れます。Claude Code にも編集させないよう、①で設定してあります。

① .claude/settings.json：秘密情報を Claude Code に読ませない設定と、講師のファイルを編集させない設定

参考（実行しない）：.claude/settings.json
{
  "permissions": {
    "deny": [
      "Read(./**/.dev.vars)",
      "Read(./**/.env)",
      "Read(./**/.env.*)",
      "Read(./secrets/**)",
      "Edit(./.github/**)",
      "Edit(./.claude/**)",
      "Edit(./backend/wrangler.jsonc)"
    ]
  }
}
この設定の意味を見る
  • permissions.deny：Claude Code にさせない操作の一覧です。ここに書いた操作は、Claude Code が頼まれても実行しません。
  • Read(./**/.dev.vars)：どのフォルダにある .dev.vars も読ませない。** は「すべてのフォルダ」という意味です。.dev.vars は Cloudflare Workers で、手元で動かすときのパスワードや API キーを書くファイルです。
  • Read(./**/.env)、Read(./**/.env.*)：.env や .env.local なども読ませない。秘密情報を書く定番のファイルです。
  • Read(./secrets/**)：secrets フォルダの中身はすべて読ませない。
  • Edit(...) の3行：自動で公開する仕組み、この設定ファイル自体、公開先の設定を、Claude Code に書き換えさせない。

Claude Code が読んだ内容は、会話の一部として AI に送られます。秘密情報を誤って読ませないよう、最初に止めておきます。

② .npmrc：公開されたばかりの怪しいパッケージを入れないための設定

参考（実行しない）：.npmrc
min-release-age=7
audit=true
2つの設定の意味を見る
  • min-release-age=7：公開されてから7日たっていないバージョンは、npm install で入れない。乗っ取られたパッケージや、有名なパッケージに似せた偽物は、公開されてすぐに見つかって消されることが多いので、数日待つだけで避けやすくなります。
  • audit=true：npm install のたびに、入れたパッケージに知られた脆弱性がないかを自動でチェックする。

ファイルの中身は、Claude Code に「.claude/settings.json を見せて」のように頼むと確認できます。

1. 全体像（アーキテクチャ）

フロントと API を1つの Cloudflare Workerから配信します。そのためフロントは /api/... を相対パスで呼ぶだけで済みます。公開は、main に push すると GitHub Actions が自動で行います（[6]）。

2. 題材と共通の流れ

題材は次の7つから班で1つ選びます。どの題材も、次の共通の流れで作ります。

① ログイン→② データを登録→③ 一覧で見る→④ 固有ロジック

①〜③はどの題材でもほぼ同じです。題材ごとの違いは ④ だけなので、ここをどう作るかが腕の見せどころです。

ログインはメールアドレスを入力するだけの簡易版です。パスワードはありません。API はリクエストヘッダ x-user-email のメールアドレスをそのまま本人とみなします。

題材カード

各題材には、社内の誰かからの依頼が来ている設定です。依頼内容と条件を読んで、困りごとを解決するには何が必要かを班で考えてください。条件はすべて満たす必要があります。それ以外の機能は自由です。

【未定】[2] 以降の進め方は、当日の環境に合わせて講師から指示します。

  • Claude Design が使えない場合は、[2] を飛ばし、[3] で spec.md から直接画面を作ることがあります。
  • 使う技術（[3] [4] のフロント・バックエンド）が変わることがあります。
  • どの場合も spec.md はそのまま使えます。技術の話を書かないのはそのためです。

作業を始める前に

  • こまめに commit する：手順が1つ終わるたびに commit してください。途中で壊れても、うまく動いていたところまで戻れます。リポジトリは講師が用意したものを使い、フォークはしません。ブランチで作業して、main にマージします。
  • main に入れたものは公開される：[6] の準備が済んだあとは、main に push するたびに自動で公開されます。手元から deploy はしません。
  • 講師のファイルを変えない：.github/、.claude/、backend/wrangler.jsonc、backend/package.json の scripts は変更しないでください（最初から入っているファイル）。
  • 秘密の値を渡さない：パスワードや API キーなどの秘密の値は、commit しないでください。Claude Code のチャットにも貼らないでください。秘密の値は backend/.dev.vars に書き、Claude Code には名前だけを伝えます（事前準備の設定で、Claude Code は .dev.vars を読めないようにしてあります）。
  • 困ったら Claude Code に相談する：エラーが出たり、思ったとおりに動かなかったりしたら、エラーメッセージと「何をしたら、何が起きたか」をそのまま Claude Code に貼って、相談しながら進めてください。公開に失敗したときは、GitHub の Actions タブで失敗した実行を開き、ログのエラーの部分を貼ります。

[1] 壁打ちで要件を決め、spec.md にまとめる

いきなり画面を作らず、まず何を作るかを班で決めます。Claude Code に聞き役をしてもらい、質問に答えながら機能やルールを炙り出します。決めるのは自分たちで、AI は質問と整理を手伝うだけです。

  1. リポジトリ直下（リポジトリのフォルダに移動するで移動したフォルダ）で Claude Code を開く。
  2. 次のプロンプトをコピーして Claude Code の入力欄に貼る。
  3. 自分の題材カードを開いて「カードの中身をコピー」を押し、プロンプトの < > の行と置き換えて送る。書き換えるのはこの1か所だけです。
  4. 質問に1つずつ、班で相談して答える。迷ったら題材カードの「ヒント：機能の例」も見てよい。
  5. 最後にまとめが出たら読み合わせ、直したいところを伝える。OK と答えると spec.md が書き出される。
  6. spec.md を commit する。
Claude Code に送る
社内向けの Web ツールを作る前に、要件を一緒に整理したい。
あなたは聞き役になって、私たち（開発チーム）に質問しながら要件を固めて。

題材カードは次のとおり。
<題材カードの「カードの中身をコピー」でコピーしたものを貼る>

進め方
- 質問は1回に1つだけ。答えやすいように、選択肢や例を添えてよい
- 次の順で聞く：困りごとの言い直し → 使う人と場面 → 機能 → ルールの細部 → 画面
- 機能やルールを決めるのは私たち。あなたは提案してよいが、私たちが選ぶまで決定扱いにしない
- 依頼者の条件は削らない。曖昧なところは「どう解釈するか」を私たちに聞く
- どの題材にも共通の流れ（ログイン → データを登録 → 一覧で見る → 固有ロジック）が入っているか確かめる
- ログインはメールアドレスを入力するだけの簡易ログインで決まっているので、聞かなくてよい
- 機能は全部で3〜5個に収める。増えすぎたら優先順位を聞いて絞る
- 全体で30分ほどで終わる量にする
- 使う技術（言語・ライブラリ・DB）やデザインの細部（色・レイアウト）は聞かない

全部決まったら、spec.md の形でまとめて見せて。
私たちが OK と言ったら、リポジトリ直下に spec.md として書き出して。

spec.md の形式
# <ツール名>
## 依頼者と困っていること
## 使う人と場面
## 機能
（3〜5個。共通の流れのどれに当たるかも書く）
## ルール
（1つずつ「ルール／違反したときどうなるか／根拠（依頼者の条件・チームで決めた）」を書く）
## 画面
（画面ごとに、何が表示されて何ができるか。レイアウトは書かない）
## やらないこと
（今回は作らないと決めたもの）

AI の提案をそのまま採用せず、「なぜそれが必要か」を班で言えるものだけ選んでください。言えないものは「やらないこと」に入れて構いません。

spec.md の完成例（送らない）
# 置き傘シェア

## 依頼者と困っていること
総務部。受付の置き傘が誰に借りられたか分からず、返ってこないまま数が減っていく。

## 使う人と場面
急に雨が降ってきた帰りがけに、社員がスマホや PC で空いている傘を探して借りる。
総務は週に1回、返っていない傘を確認する。

## 機能
1. メールアドレスでログインする（ログイン）
2. 傘を登録する。総務だけが使う（データを登録）
3. 傘ごとの貸出状況（貸出中／空き）を一覧で見る（一覧で見る）
4. 傘を借りる・返す。自分が今借りている傘を表示する（固有ロジック）
5. 3日以上返していない人を一覧で見る（固有ロジック）

## ルール
- 貸出中の傘は、別の人が借りられない／「貸出中です」と出して借りられない／依頼者の条件
- 1人が同時に借りられるのは1本まで／「先に返してください」と出して借りられない／依頼者の条件
- 誰が借りているかを一覧に表示する／（表示のルール）／依頼者の条件
- 返せるのは借りている本人だけ／「本人しか返せません」と出して返せない／チームで決めた

## 画面
- ログイン：メールアドレスを入力してログインする
- 傘の一覧：傘ごとの状態と借りている人。空いている傘には「借りる」ボタン
- 自分の傘：今借りている傘と「返す」ボタン
- 未返却の一覧（総務）：3日以上返していない人と傘

## やらないこと
- 返却期限のメール通知
- 傘の予約
